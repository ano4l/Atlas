# Atlas mobile

Atlas is a React Native + Expo application targeting iOS and Android only. The map is a custom native vector scene, drawn with react-native-svg and moved using Gesture Handler and Reanimated. It has no map SDK, provider credentials or map tiles.

## Run

From the repository root:

- Install: `corepack pnpm install --frozen-lockfile`
- Open in Expo Go: `corepack pnpm --filter mobile start`
- Compile and launch Android: `corepack pnpm --filter mobile android`
- Compile and launch iOS on a Mac: `corepack pnpm --filter mobile ios`
- Validate types: `corepack pnpm --filter mobile typecheck`
- Validate demo routing and UX state: `corepack pnpm --filter mobile test`

The root .npmrc enables hoisted dependencies for Expo native prebuild and autolinking. Safe-area handling uses react-native-safe-area-context. The app fills the device.

The map runs in SDK 58 Expo Go with React Native 0.88 and React 19.3. Use Node 22.13 or a newer supported Node release. Gesture Handler and Reanimated use Expo-compatible versions; babel-preset-expo configures the worklets plugin. Restart Metro with `--clear` after installing these native dependencies, then reload Expo Go.

## iOS compilation

The ios-simulator profile in eas.json builds a Release simulator app on EAS's macOS builders without Apple signing credentials:

`eas build --platform ios --profile ios-simulator`

Run that command from apps/mobile. The simulator artifact requires a Mac to launch. The [historical UX EAS build f6359dda](https://expo.dev/accounts/certi4no/projects/indoor-navigation-mobile/builds/f6359dda-0630-4c7f-9c17-ba9fc1ff83b8) is from 2026-10-12 and predates the custom map. The custom map has Android SDK 58 Expo Go runtime validation and an iOS development bundle check; a new standalone iOS release build remains separate. Runtime verification and previous builds are recorded in BUILD_CHECKS.md.

Native directories are generated by Expo and ignored in Git. Local iOS prebuild requires macOS or Linux; use EAS Build for iOS builds from Windows. A JavaScript export is a bundle check, not proof of successful native compilation or device execution.

## Maps and flows

The visual testing layer adds eight fictional tenants: Nook, Paper & Pine, Juniper Cafe, Petal Studio, Market Hall, Orbit, Forma and Olive Table. These appear in discovery, search, the directory and route previews, with demo identification and fictional-tenant descriptions. Shallow wall faces, glazed shop surfaces, warm concourse paving and illustrative court landscaping give the SVG scene depth. Touch footprints and the gallery route network retain the traced geometry. The camera remains overhead.

The active demo is hand-traced from the Sandton schematic supplied by the user. It has 141 approximate spaces, five visible store names and one Reference level. Unknown tenants use generated S-prefixed references. The surrounding roads, circular court and gallery arrangement follow the image. The reference is saved under assets/sandton-reference.png; the editable geometry is in src/fixtures.ts.

Routes use the local gallery graph and start beside the west marker. Unknown unit approaches end on a mapped gallery; actual entrances remain unconfirmed. Floor assignments, accessible paths, current tenancy, opening hours and real-world scale are not established by this image. Walking distances are demo estimates. Navigation plays an accelerated demo walk with pause/continue and skip-turn controls; it does not track live device movement.

The mall overview keeps Search, Directory, and Saved in the bottom dock. Tap a place to see the estimated walk and open the walking steps before starting. Active guidance highlights the next maneuver above the map and keeps remaining time, distance, and walk controls below. Search and the directory share category filters and place rows.

Drag or tap the dock handle to show or hide suggestions. Map controls move with the sheet. The camera reframes after release. Floating map controls use native regular Liquid Glass on supported iOS devices, with static materials on Android and opaque surfaces for reduced motion, reduced transparency or increased contrast.

Drag to pan, pinch around the point between your fingers, double-tap to zoom or use the 44-point zoom buttons. Close zoom reveals generated unit references. Camera framing reserves measured overlay space. Panning pauses framing; Recenter or Resume restores it. No map provider, tile service or geographic conversion is required.

See [Sandton schematic notes](../../docs/sandton-demo-map.md), [custom-map research](../../docs/custom-indoor-map-research.md) and DESIGN_SYSTEM.md.

## Preview a connected test venue

With Docker Desktop running and JDK 21 available, use two PowerShell terminals from the repository root. Start the API, import the fictional venue and publish its current version:

```powershell
.\tests\end-to-end\run-map-package-flow.ps1 -KeepApiRunning
```

For an Android emulator, set the API address and start Expo in the second terminal:

```powershell
$env:EXPO_PUBLIC_ATLAS_API_URL = "http://10.0.2.2:18080"
corepack pnpm --filter mobile start --clear
```

For a physical phone, use the computer's reachable LAN address in place of `10.0.2.2`. The phone needs a network path to the API, and builds that require HTTPS need an HTTPS API URL. The Expo bundle only receives the public URL.

Open **Map options → Fictional test venue**. Choose a ground-floor entrance, search for **Zara**, select the result and switch between **G** and **L1** to inspect both route segments. Atlas uses the published map package, backend search and a route for that same version. The position marker shows the chosen start. Each blue dot represents a destination entrance.

After opening the venue once with the updated API, restart with the API unavailable to exercise offline mode. Atlas uses the saved map, directory and graph for search and route previews. The offline banner shows when it last synced and warns that closures may have changed. Choose **Sync map** outside a simulation to reload the published package and start a new preview. Use it to pick up a closure, a publication or a rollback.

Choose **Simulate guidance** on a route preview to follow the fictional walk. The simulation shows distance to turns and the remaining route, pauses when Atlas leaves the foreground, and waits for confirmation before continuing onto the next floor.

During a simulation, choose **Simulate a missed turn** to take the next suitable side corridor. Atlas requests a new route from its mapped endpoint after sustained off-route readings. If the service becomes unreachable, it can use the saved map while retaining the step-free preference. If no route is available, the simulation pauses and offers **Retry reroute**.

Use **Correct simulated position** to pick a mapped entrance on the floor you want to start from. Atlas recalculates the route to your selected destination.

### Print and scan fictional checkpoints

From the repository root, download the currently published package and generate a print-ready sheet. Use a new output filename when you regenerate the sheet.

```powershell
$api = "http://localhost:18080"
$venue = Invoke-RestMethod "$api/v1/venues" | Where-Object slug -eq "atlas-synthetic-mall"
$mapFile = Join-Path $env:TEMP "atlas-published-map.json"
$sheetFile = Join-Path $env:TEMP "atlas-checkpoints.html"
Invoke-WebRequest "$api/v1/venues/$($venue.id)/map-package" -OutFile $mapFile
corepack pnpm --filter mobile checkpoints $mapFile $sheetFile
Invoke-Item $sheetFile
```

Print the sheet. In the simulation on a camera-capable phone, choose **Correct simulated position → Scan checkpoint**, grant camera access if prompted, and scan an entrance. Atlas pauses the simulation during correction and recalculates the route from that entrance. The code is valid for the venue and map version printed on the sheet. After publishing a new version, download its package and print a fresh sheet.

### Record navigation diagnostics

In **Settings → Navigation diagnostics**, start recording, then reproduce the issue in the fictional test venue. The report keeps up to 40 failures or offline fallbacks in memory for 30 minutes from the start of recording. It includes the operation, elapsed time, outcome, and any available HTTP status and request reference. Searches, destinations, coordinates, and sensor data stay out of the report. Stop recording to preserve the current report until it expires, share it using the system share sheet, or clear it immediately. Restarting Atlas clears the in-app report.

### Record a walk for replay

On a physical iOS or Android device, open **Map options → Settings → Walk recorder** in a development build. Choose **In hand** or **In pocket**, then start the recording. Walk with Atlas in the foreground. Stop and choose **Export replay** to save the JSON using your device's share sheet. Atlas keeps the unexported recording in memory until you leave Settings. The share sheet uses one temporary file in the app cache. A release test build can enable the recorder with `EXPO_PUBLIC_ATLAS_WALK_RECORDER=1`.

The recorder samples motion and, when available, barometric pressure. On supported phones it uses Expo DeviceMotion to capture acceleration and derive an upward acceleration sample when linear and gravity-inclusive readings align. Phones without DeviceMotion use the accelerometer. The export records the motion source, elapsed receipt time and native sensor timestamps. Replay can report steps from these unmapped sessions. A position estimate requires a known start and map-relative heading data. See the [replay instructions](../../tests/positioning-replays/README.md).

During a test walk, tap **Mark checkpoint** at each point you plan to measure. Atlas records the checkpoint number and elapsed time. Keep the corresponding local coordinates in a separate measurements file and add them during replay.

## Xcross verification

The installed Windows executable is at %LOCALAPPDATA%\\xcross\\bin\\xcross.exe, version 2.0.2. It was actually tested against this project on 2026-10-12:

- `xcross react-native --help`: command not found.
- `xcross flutter build --no-pub`: after a native iOS project was generated for the probe, failed with `pubspec.yaml not found`.
- `xcross compose build --configuration debug`: failed with `No settings.gradle.kts found`.

No successful Xcross compilation is claimed. Another React Native project's working Xcross command or wrapper is needed to reproduce that workflow. EAS compilation is independent evidence and does not count as a successful Xcross build.
